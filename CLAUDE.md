# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

GopiLang: a small, statically-typed programming language with a complete, from-scratch compiler and virtual machine — lexer, parser, semantic analyzer, bytecode generator, and VM — implemented entirely in hand-written Java 21 (no parser generators, no third-party compiler/VM libraries, no reflection in production code). The mission is deep, first-principles understanding of compiler and VM construction, built and reviewed incrementally, one class (or one opcode) at a time — this is not a "ship it fast" project. The long-term, not-yet-started goal is to rewrite the compiler in GopiLang itself for self-hosting.

Full pipeline (all stages implemented): `Gopi Source (.gopi) → Lexer → Parser/AST → Semantic Analyzer → Bytecode Generator → Bytecode Module → Virtual Machine → Output`

See [README.md](README.md) for language examples and CLI usage, [ARCHITECTURE.md](ARCHITECTURE.md) for the full package-by-package breakdown, [LANGUAGE.md](LANGUAGE.md) for the language spec and grammar, and [CONTRIBUTING.md](CONTRIBUTING.md) for coding-style rules.

## Commands

- Build: `mvn compile`
- Run all tests: `mvn test`
- Run one test class: `mvn test -Dtest=ParserTest`
- Run one test method: `mvn test -Dtest=ParserTest#elseAttachesToNearestIf` (nested `@Nested` classes: `mvn test -Dtest='ParserTest$DanglingElse#elseAttachesToNearestIf'`)
- Standalone distribution (`target/gopilang/`, with an executable `lib/gopilang.jar` and `bin/gopic` launcher): `mvn package`
- CLI tool (after `mvn compile`; `./gopic` is a thin wrapper around `java -cp target/classes com.gopilang.cli.GopiC`, so re-run `mvn compile` after any source change):
  - `./gopic <file.gopi>` — compile and run a program end-to-end
  - `./gopic --tokens <file.gopi>` — print the lexer's token stream
  - `./gopic --ast <file.gopi>` — print the parsed AST as a Unicode tree
  - `./gopic --disassemble <file.gopi>` — compile and print the generated bytecode (constant pool, function table, struct table, instructions) without running it
  - All modes share `compileToBytecode()`, which runs lexer → parser → semantic analyzer → code generator in sequence and stops at the first phase reporting errors — a later phase never sees output from a failed earlier one.
- Sample programs live in `examples/*.gopi`; `examples/semantic/` has one small program per semantic-diagnostic category (undefined variables, shadowing, duplicate declarations, use-before-assignment, unreachable code, etc.) — useful as regression material and as executable documentation of what each check catches.

Test suites (`src/test/java/com/gopilang/`) are organized by pipeline stage — `lexer/`, `parser/`, `semantic/`, and (since the `&&`/`||` short-circuit codegen milestone) `bytecode/`, `vm/`.

## Architecture

### Package layout mirrors pipeline stage, not feature

`lexer/`, `parser/`, `ast/`, `semantic/`, `bytecode/`, `vm/` are pipeline stages; `types/`, `util/`, `errors/`, `printer/` are cross-cutting concerns used by multiple stages; `cli/` is the entry point. When adding to a stage, put new classes in the matching package — don't invent a new package for a single class unless it's a genuinely new stage. No stage reaches backward into an earlier one, and no stage re-validates something an earlier stage already guaranteed: by the time bytecode generation runs, the AST is known type-correct and every identifier is known resolved; by the time the VM runs, the bytecode is assumed valid.

### Error/diagnostic architecture — two parallel hierarchies, don't confuse them

- **`GopiError` (abstract, extends `RuntimeException`)** and its subclasses `LexerException`, `ParseError` are **internal, phase-local control-flow signals only** — thrown to unwind out of a broken token/statement, caught immediately within the same phase, and converted to a `Diagnostic` at the catch site. They never escape the phase that threw them. Semantic analysis has no `GopiError` subclass at all — it never throws, because by the time it runs the tree's structure is already known-valid, so every semantic problem is locally recoverable (see poison-type note below).
- **`Diagnostic`** (a plain immutable record: phase, range, message, suggestion) is the only thing that crosses phase boundaries. Each phase (`Lexer`, `Parser`, `SemanticAnalyzer`) owns its own `DiagnosticReporter` (self-contained, not injected — merging multiple phases' diagnostics into one view is the CLI's job, not each phase's).
- Recovery strategy differs by phase and is deliberate, not incidental: lexer/parser use panic-mode (`Parser.synchronize(insideBlock: boolean)` — the boolean distinguishes recovering inside a block, where a stray `}` must NOT be consumed since the enclosing loop needs to see it, from recovering at the top level, where it must be consumed or the parser hangs). Semantic analysis uses no synchronization at all — an unresolved/invalid expression simply gets no entry in `SemanticModel`'s maps (absence = poison), and every downstream check that reads an absent entry silently skips its own check rather than reporting a cascade. This is why one root cause never produces more than one diagnostic, and it's why `ErrorPhase.TYPE` diagnostics (type mismatches) are distinct from `ErrorPhase.SEMANTIC` ones (resolution failures, duplicate/shadowed declarations).
- Bytecode generation and the VM never produce `Diagnostic`s at all: a missing resolution or invalid state at this point means an earlier phase failed to catch something, and is treated as an internal invariant violation (`IllegalStateException`), not a user-facing error.

### AST — sealed, immutable records; extended (not reopened) for arrays; no Visitor pattern

`ASTNode` (sealed: `Program, Parameter, FunctionDeclaration, Stmt, Expr`), `Stmt` (sealed, 7 concretes), `Expr` (sealed, 11 concretes) are all immutable records. v1 shipped seven `Expr` kinds (`LiteralExpression`, `VariableExpression`, `GroupingExpression`, `UnaryExpression`, `BinaryExpression`, `AssignmentExpression`, `FunctionCallExpression`); v2 Milestone 1 (arrays) added four more — `NewArrayExpression` (`new elementType[size]`), `ArrayAccessExpression` (`array[index]` read), `ArrayLengthExpression` (`array.len()`), `IndexAssignmentExpression` (`array[index] = value`) — rather than reopening any of the original seven. `IndexAssignmentExpression` is deliberately its own node rather than generalizing `AssignmentExpression`'s `String` target to an arbitrary lvalue, so the original, well-tested plain-variable assignment path stays untouched. Every AST-consuming operation (semantic analysis, `AstPrinter`, `CodeGenerator`) is a plain `switch` over the sealed hierarchy in its own class, relying on Java 21's exhaustive pattern-matching switch for the same "every case must be handled" guarantee a Visitor would give — not a new `accept()` method on the nodes. Follow this pattern for any new AST-consuming operation.

`FunctionDeclaration` is intentionally *not* part of the `Stmt` hierarchy (nested functions are disallowed — it only ever appears in `Program.functions()`). `Program` holds only `List<FunctionDeclaration>` — no top-level variables or statements; GopiLang requires a `void main()`-equivalent entry point (`none main()`), validated by `SemanticAnalyzer.validateMainFunction()` (not the parser — parsing `none main(){}` and `none foo(){}` is structurally identical, so "does this program have a valid entry point" is a whole-program semantic question, not a syntactic one).

### The type system got a real extension in v2, not just new AST nodes

Arrays required `FunctionSymbol`/`VariableSymbol` to switch from bare `PrimitiveType` to `types.TypeRef` (element type + "is this an array") for `type`/`returnType`/`parameterTypes`, threaded through everywhere a declared or computed type is stored (`Parameter`, `VariableDeclaration`, `FunctionDeclaration`, `SemanticModel.expressionTypes()`). `TypeRules.resultOfUnary`/`resultOfBinary` stay `PrimitiveType`-only on purpose — arrays never reach them, because `typeOf` rejects an array operand for every operator before calling in — while `isAssignable`/`isReturnCompatible`/`isArgumentCompatible`/`isPrintable` are `TypeRef`-based, since those checks must know about arrays (array assignment requires an exact element-type match, with no numeric-widening).

### Semantic analysis is multi-pass by necessity, and never mutates the AST

`SemanticAnalyzer` runs two passes over `Program`: Pass 1 (`registerFunctions`) registers every function's signature into a flat, name-keyed table *before* any body is analyzed, which is what makes forward references and mutual recursion between functions resolve correctly. Pass 2 (`analyzeFunction`/`analyzeStatement`/`analyzeExpr`) walks each body doing scope management and identifier resolution, and is *also* where statement-level type checking and reachability analysis are woven in (extending the same switch, not a separate traversal) — only expression typing (`typeOf`) is its own standalone recursive method, since it's invoked from many different statement contexts.

Its output, `SemanticModel`, is a separate immutable record (function table, variable/assignment-target/call resolutions, expression types) — never written onto the AST nodes. This is why the maps use two different `Map` implementations and it matters which: `functionTable` is `String`-keyed (ordinary equality is correct — two occurrences of the name "add" should collide) and built with `Map.copyOf`; the other four maps are keyed by AST node instances and **must** use `IdentityHashMap` semantics (two structurally-equal-but-distinct nodes, e.g. two `VariableExpression("x", sameRange)` at different source occurrences, must not collide) — note that `Map.copyOf()` on an `IdentityHashMap` silently discards identity semantics (or throws `IllegalArgumentException: duplicate key` if a real collision exists), so `SemanticModel`'s compact constructor rebuilds those four via `new IdentityHashMap<>(source)` + `Collections.unmodifiableMap`, not `Map.copyOf`. If you add a new node-keyed map anywhere, default to `IdentityHashMap` for the same reason.

`TypeRules` (pure static methods, zero dependency on `Scope`/`SemanticModel`/the AST node hierarchy) holds the actual type-compatibility table and is deliberately separate from `SemanticAnalyzer` for independent testability.

`Scope` is a mutable, parent-linked chain (one `Scope` per block), intentionally mutable/non-persistent — narrowly-scoped, single-traversal mutation, not shared or long-lived, unlike the AST. Shadowing a variable from an enclosing scope is a reported error, not silently allowed (Java-style, not C-style).

### Definite assignment tracks state on `SemanticAnalyzer`, never on `VariableSymbol`

`SemanticAnalyzer.currentAssigned` (a `Set<VariableSymbol>`, identity-based via `Collections.newSetFromMap(new IdentityHashMap<>())` — required, not just safer, for the same shadowing reason as `SemanticModel`'s maps) tracks which symbols are known-assigned on the current path. It is mutable field state exactly like `currentScope`, not a field added to `VariableSymbol` itself — mutating a value shared across multiple frozen maps would reintroduce the aliasing risk immutability elsewhere in this codebase exists to prevent. Branch merging at `if`/`else` intersects the then/else branches' independent snapshots (assigned only if *both* branches assigned it, or there's no `else` at all — mirroring reachability's "no else, never guaranteed" rule); `while` conservatively discards anything the body assigns, uniformly, with no `while(true)` special case (unlike reachability, which does special-case it for returns).

### `bytecode` — builder-then-freeze code generation, a fixed instruction shape

`CodeGenerator` mirrors `SemanticAnalyzer`/`SemanticModel`'s shape exactly: mutable accumulators (deduplicated constant pool via `constantIndex`, per-function local-slot map, function-index map) filled in while walking the AST, assembled into one immutable `BytecodeModule` at the end (`generate()`). `generate()` assigns every function a stable index in declaration order, emits the program's two-instruction entry stub (`CALL <index of main>; HALT` — always instructions 0 and 1, so the VM always knows where to start regardless of declaration order), then compiles each function. Forward jumps (`if`/`else`, `while`) use backpatching: a placeholder operand (`-1`) is emitted and its instruction index remembered, then overwritten in place once the true target is known — `Instruction` is an immutable `(Opcode, int operand)` record, so backpatching replaces the list entry wholesale (`instructions.set(index, new Instruction(...))`) rather than mutating a field. Every function always gets a trailing unconditional `RETURN` emitted, even when every path already returns, so a function body never "falls off the end" of the shared instruction stream.

`Opcode` is a closed, deliberately small instruction set (30 opcodes) — every type-specific decision was already resolved by semantic analysis, so opcodes don't need per-type variants. Arrays (`NEW_ARRAY`/`ARRAY_GET`/`ARRAY_SET`/`ARRAY_LENGTH`) and structs (`NEW_STRUCT`) both operate on a plain `Object[]` reference; GopiLang has no dedicated runtime array or struct wrapper, consistent with every scalar already being boxed as `Object` in the VM.

### `vm` — a stack machine with one shared instruction stream

One flat instruction stream spans every function in the program; each active call gets its own `Frame` (local-variable slots sized by `slotCount()` + its own operand stack + return address). `VirtualMachine.run()` is a fetch-decode-execute loop over a `Deque<Frame>` call stack. `CALL` pops the callee's arguments off the caller's operand stack (last-pushed argument lands in the highest local slot, matching left-to-right argument compilation), pushes a new `Frame`, and jumps to the callee's `codeStart`. `RETURN` pops the current frame, optionally carries a value back onto the now-current caller's stack, restores `pc`, and terminates the program if no caller frame remains. Recursion needs no special handling — two simultaneously-active calls to the same function are just two distinct `Frame`s on the stack. `pc` is incremented *before* opcode dispatch, so `JMP`/`JMP_IF_FALSE` land exactly on their target index by simply overwriting `pc` with the instruction's operand.

### Current implementation state

Every pipeline stage — lexer, parser/AST, semantic analysis, bytecode generation, VM — is implemented and exercised through the CLI. v2 Milestone 1 added arrays (parsing, type-checking, codegen, and VM opcodes) end-to-end. `&&`/`||` short-circuit compilation (previously a tracked gap — `CodeGenerator` threw `UnsupportedOperationException` for them) is now implemented: both compile to conditional jumps reusing the existing `JMP`/`JMP_IF_FALSE` opcodes (no new opcodes, no VM changes), evaluating the right operand only when the left doesn't already determine the result — see `CodeGeneratorTest`/`VirtualMachineTest` (the first test suites for the `bytecode`/`vm` packages) and `examples/short_circuit.gopi`.

**v3 Milestone S1 (struct declarations)**: top-level `struct Name { field* }` declarations parse and register into a new `structTable` (`StructSymbol`, mirroring `FunctionSymbol`'s shape), with duplicate-struct-name and duplicate-field-name detection reusing the exact patterns `registerFunctions()`/`analyzeFunction()` already use. Fields are plain `Parameter`s (no new "Field" node) and are primitive-typed only.

**v3 Milestone S2 (struct names as types, parser-only)**: a struct name became accepted wherever a variable type, parameter type, or return type was expected, but semantic analysis blanket-rejected every occurrence with a temporary "not supported yet" stub — superseded by S3 below (the S2-era `Optional<String>` struct-name fields it added to `Parameter`/`VariableDeclaration`/`FunctionDeclaration`, and the `STRUCT_TYPE_PLACEHOLDER`/`ParsedType` parser plumbing that went with them, no longer exist — S3 folds the struct name directly into `TypeRef` instead, see below).

**v3 Milestone S3 (real struct type system, done)**: struct types are now fully integrated — nominal typing, undefined-struct resolution, forward references, assignment/argument/return compatibility, struct-operand rejection for printing and operators, and cyclic-struct detection (both direct and indirect) — with arrays of structs legal everywhere a type is legal (`Point[] points;`, `none foo(Point[] p)`, `Point[] make()`, and as a struct field). `TypeRef` gained one additive field, `Optional<String> structName`, alongside its existing `elementType`/`isArray` (`elementType` has no meaning whenever `structName` is present — a placeholder value only, needed because `CodeGenerator` is frozen and reads `elementType()` directly at two call sites; every check this milestone adds or touches consults `structName()` first). This let `Parameter`/`VariableDeclaration`/`FunctionDeclaration` revert to their pre-S2 one-`TypeRef`-field shape — struct identity now lives inside the type itself, not a separate companion field. `Parser.parseDeclaredType()` is the one production used for every type position (field, parameter, return type, variable), `declaredType ::= type | IDENTIFIER ("[" "]")?` — struct fields are no longer restricted to primitives, since real struct-in-struct composition is exactly what cycle detection needs to check. `TypeRules.isAssignable` treats a struct type nominally (name equality, never structural, never widened) after checking array-ness matches exactly; `isPrintable` rejects any struct type. `SemanticAnalyzer.registerStructs()` gained two follow-up steps after its existing registration loop: resolving each field's own type (`resolveDeclaredType()`, also called from `registerFunctions()`/`analyzeStatement`'s `VariableDeclaration` case for parameters/returns/variables) and `detectStructCycles()` — a standard `seen`/`onPath` DFS over the struct-name graph, with an edge for every *non-array* struct-typed field (an array field is a runtime reference, not inline storage, so it can't create an unbounded-size cycle — `struct Node { Node[] children; }` is legal, `struct Node { Node next; }` is not). No bytecode opcode or VM behavior exists — `CodeGenerator`/`VirtualMachine` remain completely untouched; the only reason this is safe is that no expression in the grammar can produce a struct-typed value without construction or field access, so a struct-typed declaration always type-checks to something inert at runtime (see `TypeRef`'s own javadoc for the full reasoning).

**v3 Milestone S4 (struct construction, done)**: `new StructName(arguments...)` is now real, runtime-constructible syntax — the S3-era invariant that "no expression in the grammar can produce a struct-typed value" no longer holds, replaced by an equally deliberate one: a struct instance is a plain `Object[]` at runtime (one slot per field, declaration order), exactly matching how arrays already have no dedicated wrapper type. `NewStructExpression(String structName, List<Expr> arguments, SourceRange range)` is a new `Expr` variant, shaped identically to `FunctionCallExpression`. `Parser.parsePrimary()`'s `KW_NEW` branch dispatches on the single token after `new` (a primitive keyword → the untouched array-creation path; an `IDENTIFIER` → construction) — the two token sets are disjoint, so no lookahead beyond that one token is needed; the argument-list parsing itself is `parseArguments()`, extracted out of `parseCall()` and shared by both. `SemanticAnalyzer` treats construction exactly like a function call: `analyzeExpr` recurses into arguments and resolves the struct name via the *existing* `resolveDeclaredType()` (reused verbatim, not a parallel check); `typeOf` checks argument count/type against `StructSymbol.fields()` using the *unmodified* `TypeRules.isArgumentCompatible()`, and yields the construction's own `TypeRef(..., Optional.of(structName))` — the identical S3 representation. `SemanticModel` gained no new map for this — `CodeGenerator` derives the `StructSymbol` it needs entirely from information already there: `expressionTypes().get(construction)` → `TypeRef.structName()` → `structTable()`. `CodeGenerator` builds a `Map<StructSymbol, Integer> structIndices` inside itself (never exposed to `SemanticModel`), mirroring `functionIndices` exactly, and `BytecodeModule` gained a fourth list, `structs(): List<BytecodeStruct>` (a new record, `(name, fieldCount)`, mirroring `BytecodeFunction`'s role), addressed by index the same way `functions()` is addressed by `CALL`. The one new opcode, `NEW_STRUCT <structIndex>`, evaluates constructor arguments left-to-right then pops that struct's field count off the operand stack in reverse — textually the same idiom `CALL` already uses for its own parameters — and pushes the resulting `Object[]`. `CALL`/`RETURN`/`LOAD`/`STORE` needed zero changes: they already move `Object` values with no type-specific logic, so a struct passes through them exactly as an array already does.

**v3 Milestone S5 (field access and assignment, done)**: `point.x` (read) and `point.x = value` (write), with arbitrary chaining (`point.inner.left.x`, `arr[0].x`, `box.corner.x = value`) — the last real gap in struct support, closed with **zero VM changes and zero new opcodes**. `Expr` gained two more variants, `FieldAccessExpression(Expr target, String fieldName, SourceRange range)` and `FieldAssignmentExpression(Expr target, String fieldName, Expr value, SourceRange range)` — `target` is a general `Expr` (not narrowed to a bare variable), which is what lets a field access chain onto any expression that types to a struct. `Parser.parseCall()`'s suffix handling widened from "at most one trailing suffix" to a loop over any number of them (`()`, `[]`, `.len()`, `.IDENTIFIER`) so chains parse at all, and `parseAssignment()` gained a third lvalue case (`FieldAccessExpression` → `FieldAssignmentExpression`) alongside its existing variable/array-index cases. `SemanticAnalyzer.typeOf` types the target, rejects non-struct targets and undeclared field names (a new `resolveField()` helper, reused verbatim by both node kinds, scanning `StructSymbol.fields()` directly — no cache), and for assignment checks the value's type against the field's declared type with the unmodified `TypeRules.isAssignable()`; both record their resolved type into `expressionTypes()` exactly like every other expression, so no new `SemanticModel` map was needed. The entire runtime trick is that a struct is already a plain `Object[]` (since S4) — so `CodeGenerator` resolves a field name to its declaration-order integer index at compile time (`fieldIndex()`, a plain linear scan, no caching, no runtime metadata) and compiles `point.x` as `PUSH_CONST <index>; ARRAY_GET` and `point.x = value` as `PUSH_CONST <index>; <value>; ARRAY_SET` — reusing the exact two array opcodes `ArrayAccessExpression`/`IndexAssignmentExpression` already used, since the VM cannot tell a struct's `Object[]` apart from an array's. `ARRAY_SET`'s existing "push the assigned value back" behavior is what makes chained field assignment (`a.x = b.x = 5`) work with no new bookkeeping. `Opcode`, `Instruction`, `VirtualMachine`, `Frame`, `BytecodeModule`, `BytecodeFunction`, `BytecodeStruct`, `BytecodeDisassembler`, `TypeRules`, `TypeRef`, `PrimitiveType`, `StructSymbol`, `SemanticModel`, `StructDeclaration`, and `Parameter` all stayed at zero diff for this milestone.

Struct support is now **feature-complete except for one deliberate, tracked gap**: there is still no way to construct an array of structs (`new Point[5]` stays a parse error — `Point[]` remains a legal *type* with no way to produce a value of it). There is also no method-call syntax (`point.foo()` — GopiLang structs have no attached functions, and none are planned) and no reflection or dynamic field names (a field access always names its field with a literal identifier known at parse time). See [LANGUAGE.md's Structs section](LANGUAGE.md#structs) for the full detail. **S6** (not yet started) is planning/final-audit only — no further struct language feature is currently planned.

Remaining known, tracked gaps (see [README.md](README.md#future-roadmap) and [CONTRIBUTING.md](CONTRIBUTING.md#known-tracked-gaps) — these are deliberate, not oversights, so don't "fix" them without checking there first):

- Bytecode serialization (`BytecodeWriter`/`BytecodeReader`, writing a `BytecodeModule` to a `.gbc` file and reading it back) doesn't exist — a compiled module only ever lives in memory within one process run.
- Self-hosting (rewriting the compiler in GopiLang itself) and a real debugger (breakpoints/single-stepping against `Frame`/the call stack) are long-term, not-yet-started goals.

# Architecture

This document explains how GopiLang's compiler and VM are put together: the pipeline, the responsibility of every package, and the major classes within each. For building, installing, and running `gopic`, see [README.md](README.md#installing-gopic); for the language itself, see [LANGUAGE.md](LANGUAGE.md).

## The Pipeline

```
Gopi Source (.gopi)
        │
        ▼
      Lexer                source text → List<Token>
        │
        ▼
      Parser                tokens → AST (Program)
        │
        ▼
Semantic Analyzer            AST → SemanticModel (scope/type/reachability/definite-assignment checks)
        │
        ▼
 Bytecode Generation          AST + SemanticModel → BytecodeModule
        │
        ▼
  Virtual Machine             executes a BytecodeModule
```

Each arrow is a real, separate stage with its own class and (where relevant) its own diagnostic-reporting mechanism. No stage reaches backward into an earlier one, and — critically — no stage re-validates something an earlier stage already guaranteed. By the time bytecode generation runs, the AST is known type-correct and every identifier is known resolved; by the time the VM runs, the bytecode is assumed valid. This is a deliberate design principle throughout the codebase, not an accident of how it was built incrementally.

Package layout mirrors this pipeline directly — one package per stage, plus a few cross-cutting concerns used by multiple stages.

---

## `lexer` — Source Text → Tokens

**Responsibility**: turn raw `.gopi` source text into a flat sequence of tokens.

- **`Lexer`** — hand-written character-by-character scanner. Recognizes keywords, identifiers, literals (`num`, `dec`, `text`, `flag`), operators, and punctuation. Skips whitespace and `//` line comments. Recovers from a bad character or malformed literal via panic-mode: it catches its own `LexerException`, converts it to a `Diagnostic`, and resumes scanning from the next character — so one bad token doesn't abort the whole file.
- **`Token`** — one lexical unit: its `TokenType`, lexeme text, optional literal value, and source location.
- **`TokenType`** — the closed enum of every token kind the lexer can produce.
- **`LexerException`** — an internal, phase-local control-flow signal (extends `GopiError`) thrown to unwind out of a broken token and caught immediately within `Lexer` itself. It never escapes the lexer.

## `parser` — Tokens → AST

**Responsibility**: turn a token stream into a `Program` (the root AST node), with no parser-generator involved — every production is a hand-written recursive-descent method.

- **`Parser`** — one method per grammar production (see [LANGUAGE.md](LANGUAGE.md#grammar-overview) for the full grammar). Expression parsing is precedence-climbing: `parseAssignment → parseLogicalOr → parseLogicalAnd → parseEquality → parseComparison → parseTerm → parseFactor → parseUnary → parseCall → parsePrimary`, each level handling one precedence tier and delegating to the next for its operands. Recovers from a syntax error via panic-mode synchronization; `Parser.synchronize(insideBlock)` distinguishes recovering inside a block (where a stray `}` must not be consumed, since the enclosing block-parsing loop needs to see it) from recovering at the top level (where it must be consumed or the parser would hang). As of v3 Milestone S3, `parseDeclaredType()` (`declaredType ::= type | IDENTIFIER ("[" "]")?`) is the ONE type production used for every type position — a field, a parameter, a return type, or a variable — replacing the S2-era split where fields alone stayed primitive-only; a bare `IDENTIFIER` there is unambiguously a struct name, no lookahead needed, since the grammar already mandates a type at those positions, and an optional trailing `[]` marks "array of that struct" exactly like a primitive type's own array suffix. Statement-start dispatch is the one place real ambiguity exists: `Point p;` vs `p = 5;` vs `foo();` (all starting `IDENTIFIER`), and `Point[] arr;` vs `arr[i] = 5;` (both starting `IDENTIFIER LEFT_BRACKET`) — both resolved by `isStructTypedDeclarationStart()` using a small, fixed lookahead (`checkAt(offset, TokenType)`, generalized from S2's single-token `checkNext`): two `IDENTIFIER`s in a row, or `IDENTIFIER LEFT_BRACKET RIGHT_BRACKET` (an index expression can never be empty, so that shape is unambiguously a type suffix, never an index). As of v3 Milestone S5, `parseCall()`'s trailing-suffix handling widened from "at most one suffix" to a `while (true)` loop over any number of suffixes (`"(" arguments? ")"`, `"[" expression "]"`, `"." "len" "(" ")"`, `"." IDENTIFIER`) — struct field access needs arbitrary chaining (`point.inner.left.right`, `arr[0].x`, `foo().x`), which the old single-suffix shape couldn't express. This widening is safe for the pre-existing suffixes too: a second `(` after a call (`foo()()`) still fails the existing "only a plain function name can be called" check, since neither a `FunctionCallExpression` nor a `FieldAccessExpression` is ever a `VariableExpression` — so a method-call shape (`point.foo()`) is rejected the same way, one token later, with no dedicated "no methods" check needed anywhere. `parseAssignment()`'s lvalue check gained a third case (`FieldAccessExpression` → `FieldAssignmentExpression`) alongside its existing `VariableExpression`/`ArrayAccessExpression` cases, using the same right-recursive shape that already makes chained assignment work.
- **`ParseError`** — the parser's internal control-flow signal, exactly analogous to `LexerException`: thrown to unwind out of a broken statement/expression, caught within `Parser`, converted to a `Diagnostic`, never escapes the phase.

## `ast` — The AST Node Types

**Responsibility**: define the tree shape every later stage consumes. Frozen for v1's own seven expression kinds; v2 Milestone 1 (arrays) extended the sealed `Expr` hierarchy with four more rather than reopening any of the original seven — still sealed, immutable records, no `accept()`/Visitor pattern.

- **`ASTNode`** — sealed root: `Program`, `Parameter`, `FunctionDeclaration`, `StructDeclaration`, `Stmt`, `Expr`.
- **`Stmt`** (sealed, 7 concretes) — `BlockStatement`, `VariableDeclaration`, `IfStatement`, `WhileStatement`, `ReturnStatement`, `PrintStatement`, `ExpressionStatement`.
- **`Expr`** (sealed, 14 concretes) — the original seven (`LiteralExpression`, `VariableExpression`, `GroupingExpression`, `UnaryExpression`, `BinaryExpression`, `AssignmentExpression`, `FunctionCallExpression`) plus four array-specific nodes added in v2 Milestone 1 (`NewArrayExpression`, `ArrayAccessExpression`, `ArrayLengthExpression`, `IndexAssignmentExpression` — kept as its own node rather than generalizing `AssignmentExpression`'s `String` target to an arbitrary lvalue) plus one struct-specific node added in v3 Milestone S4 (`NewStructExpression(String structName, List<Expr> arguments, SourceRange range)`, `new StructName(arguments...)`, shaped identically to `FunctionCallExpression` — the struct name is a raw string, resolved by `SemanticAnalyzer` against `structTable()` exactly like a callee name is resolved against `functionTable()`) plus two more struct-specific nodes added in v3 Milestone S5: `FieldAccessExpression(Expr target, String fieldName, SourceRange range)` (`target.fieldName`) and `FieldAssignmentExpression(Expr target, String fieldName, Expr value, SourceRange range)` (`target.fieldName = value`) — kept as their own nodes rather than generalizing `AssignmentExpression`, the same reasoning `IndexAssignmentExpression` already established for array elements. `target` is a general `Expr`, not narrowed to a bare variable, which is what lets `point.inner.left.x`, `arr[0].x`, `foo().x`, and `new Point(1).x` all reuse the same node — the field name is resolved later against the target's own resolved struct type, exactly like `FunctionCallExpression.calleeName()` is resolved against the function table.
- **`Program`** — holds `List<FunctionDeclaration>` and, since v3 Milestone S1, `List<StructDeclaration>`; there are no top-level variables or statements. `FunctionDeclaration`/`StructDeclaration` are deliberately *not* part of `Stmt` (neither functions nor structs can be nested).
- **`StructDeclaration`** (v3 Milestone S1) — a top-level `struct Name { field* }` declaration. Each field is represented as a plain `Parameter` (type + name) rather than a new "Field" record, since the shapes are identical — mirrors how `FunctionDeclaration.parameters()` already works. Still declarations-only itself: `NewStructExpression`/`FieldAccessExpression`/`FieldAssignmentExpression` (above) are what represent *using* a struct — constructing a value, reading a field, writing a field.
- **`Parameter`, `VariableDeclaration`, `FunctionDeclaration`** — each holds exactly one `TypeRef` field (`type`/`type`/`returnType`), their original pre-S2 shape. S2 had temporarily added a companion `Optional<String>` struct-name field to each, worked around like that only because `TypeRef` itself was off-limits at the time; v3 Milestone S3 lifted that restriction and folded the struct name directly into `TypeRef` instead (see `types.TypeRef` below), so the companion fields were removed as redundant rather than carried forward.
- **`BinaryOperator`**, **`UnaryOperator`** — closed enums for each operator family.

Every operation over the AST (semantic analysis, `AstPrinter`, `CodeGenerator`) is a plain `switch` over these sealed hierarchies in its own class, relying on Java 21's exhaustive pattern-matching switch for the same "every case handled" guarantee a Visitor would give — without adding an `accept()` method to every node.

## `semantic` — Semantic Analysis

**Responsibility**: validate a parsed `Program` (scope, types, reachability, definite assignment) and produce a `SemanticModel` the rest of the pipeline can trust without re-checking.

- **`SemanticAnalyzer`** — now a three-pass analyzer as of v3 Milestone S1. Pass 1a (`registerStructs`) registers every struct's field list into `structTable`, reporting duplicate struct names and duplicate field names within one struct (reusing a throwaway `Scope`'s existing `define()` duplicate-detection for the latter — the exact same mechanism `analyzeFunction` already uses for duplicate parameters). Pass 1b (`registerFunctions`) registers every function's signature into a flat table *before* any body is analyzed, so forward references and mutual recursion resolve correctly; structs register first specifically so a function signature could, in a later milestone, already refer to a struct declared further down the file. Pass 2 walks each function body doing scope management, identifier resolution, statement-level type checking, and reachability analysis all in the same traversal (expression typing, `typeOf`, is the one standalone recursive method, since it's called from many statement contexts). Also runs `validateMainFunction()` — checking for a valid `none main()` — as a final whole-program check. Struct and function names are deliberately separate namespaces (no cross-check between `structTable` and `functionTable`) — resolved by grammatical position, not a shared name registry. As of v3 Milestone S3, `registerStructs()` gained two follow-up steps after its existing per-declaration registration loop, both needing the *complete* `structTable` and so unable to run interleaved with it: a second per-declaration loop resolving each field's own type via `resolveDeclaredType()` (also called from `registerFunctions()` for parameter/return types, and from the `VariableDeclaration` case of `analyzeStatement()` for local variables) — one "undefined struct 'X'" diagnostic wherever a `TypeRef.structName()` doesn't resolve in `structTable`, mirroring "undefined function"/"undefined variable" exactly — and `detectStructCycles()`, a standard `seen`/`onPath` DFS over the struct-name graph (an edge for every *non-array* struct-typed field; an array field never contributes an edge, since it's a runtime reference rather than inline storage and so can never make a struct's size unbounded), reporting one diagnostic per back-edge found, at the field that creates it. A struct that resolves needs no further "resolved" marker — its `TypeRef` already carries the real name, so `TypeRules`'s nominal comparisons work directly off it. The S2-era blanket `checkNotStructType()` stub no longer exists. As of v3 Milestone S4, `NewStructExpression` is handled exactly like `FunctionCallExpression` in both `analyzeExpr` (recurse into arguments, then resolve the struct name — by calling `resolveDeclaredType()` verbatim, not a parallel check) and `typeOf` (argument-count/type checking against `StructSymbol.fields()`, via the unmodified `TypeRules.isArgumentCompatible()`, yielding a `TypeRef(..., Optional.of(structName))`). No new `SemanticModel` map exists for construction resolution — `CodeGenerator` derives the `StructSymbol` it needs from `expressionTypes()` + `structTable()`, the same two accessors already used for everything else. As of v3 Milestone S5, `FieldAccessExpression`/`FieldAssignmentExpression` are handled the same way structurally, but with genuinely new logic, not a reuse of an existing check: `analyzeExpr` recurses into the target (and, for assignment, the value); `typeOf` types the target, rejects it if it isn't struct-typed (`"cannot access field '...' on non-struct type '...'"`, `ErrorPhase.TYPE`) or if the field name isn't declared on that struct (`resolveField`, `"struct '...' has no field '...'"`, `ErrorPhase.SEMANTIC` — one small helper reused verbatim by both node kinds, a straight scan of `StructSymbol.fields()`, no cache), and for assignment additionally checks the value's type against the field's declared type with the unmodified `TypeRules.isAssignable()` (`"cannot assign '...' to field of type '...'"`, `ErrorPhase.TYPE`). Each resolved access/assignment records its own type (the field's `TypeRef`) into `expressionTypes()` exactly like every other typed expression — no new `SemanticModel` map here either; `CodeGenerator` recovers the *target's* struct by reading `expressionTypes().get(target)` (not the access/assignment expression itself) and following `structName()` into `structTable()`, the same two-accessor pattern S4 established.
- **`SemanticModel`** — the analyzer's immutable output: struct and function tables plus four node-keyed resolution/type maps. Both tables are `String`-keyed (ordinary equality is correct there); the other four *must* use `IdentityHashMap` semantics, since two structurally-identical-but-distinct AST nodes (e.g. two separate `x` references) must never collide — the compact constructor rebuilds them as genuine `IdentityHashMap`s rather than using `Map.copyOf` (which would silently discard identity semantics, or throw on a real collision).
- **`Scope`** — a mutable, parent-linked chain, one per block. Deliberately mutable and short-lived (unlike the AST's immutability) since it only exists for the single resolution pass — also reused, standalone (`new Scope(null)`), purely for its duplicate-name detection during `registerStructs`. Shadowing a variable from an enclosing scope is a reported error.
- **`TypeRules`** — pure static type-compatibility rules (assignability, binary/unary operator result types, printability), with zero dependency on `Scope`/`SemanticModel`/the AST — kept separate specifically so it's independently testable. `resultOfUnary`/`resultOfBinary` stay `PrimitiveType`-only (arrays and structs never reach them — `typeOf` rejects an array-typed or struct-typed operand for every operator before calling in); `isAssignable`/`isReturnCompatible`/`isArgumentCompatible`/`isPrintable` are `TypeRef`-based. `isAssignable` checks array-ness matches exactly first (unchanged rule, no widening), then — as of v3 Milestone S3 — checks `structName()`: if present on either side, compatibility is exact name equality (nominal typing, never structural, never widened); only once neither side is a struct does the original primitive rule (equal types, or `int` widening to `float`) apply. `isPrintable` rejects any struct type the same way it already rejected arrays.
- **`FunctionSymbol`**, **`VariableSymbol`** — resolved-declaration records (name, type, declaration site) that `SemanticModel`'s maps point at. Their `type`/`returnType`/`parameterTypes` fields are `types.TypeRef` (element type + "is this an array" +, as of v3 Milestone S3, an optional struct name), not bare `PrimitiveType` — the minimum type-system extension arrays required, added in v2 Milestone 1 and threaded through everywhere a declared or computed type is stored (`Parameter`, `VariableDeclaration`, `FunctionDeclaration`, `SemanticModel.expressionTypes()`). `TypeRef.structName` is an additive `Optional<String>` field alongside the original `elementType`/`isArray` — `elementType` has no meaning whenever `structName` is present (a placeholder value only, needed because `CodeGenerator` is frozen and reads `elementType()` directly at two call sites; every check `TypeRules`/`SemanticAnalyzer` add or touch for S3 consults `structName()` first).
- **`StructSymbol`** (v3 Milestone S1) — a resolved struct declaration (name, its `List<Parameter>` fields, declaration site), registered into `SemanticModel.structTable()`. Mirrors `FunctionSymbol`'s shape and role exactly.

Semantic analysis never throws — there is no `GopiError` subclass for this phase. An unresolved or invalid expression simply has no entry in `SemanticModel`'s maps ("absence = poison"), and every downstream check that reads an absent entry silently skips its own check rather than cascading a second diagnostic from the same root cause.

## `bytecode` — Code Generation & the Bytecode Data Model

**Responsibility**: lower a validated `Program` + `SemanticModel` into a `BytecodeModule` the VM can execute.

- **`Opcode`** — the closed instruction set: 30 opcodes across constants, locals, arithmetic, comparison, control flow, functions, arrays, structs, I/O, and stack operations. Deliberately small compared to JVM bytecode — every type-specific decision (which numeric type, which operator variant) was already resolved by semantic analysis, so the instruction set itself doesn't need per-type opcode variants. The four array opcodes (`NEW_ARRAY`/`ARRAY_GET`/`ARRAY_SET`/`ARRAY_LENGTH`, added in v2 Milestone 1) and the one struct opcode (`NEW_STRUCT`, added in v3 Milestone S4) all operate on a plain `Object[]` reference — GopiLang arrays and structs have no dedicated runtime wrapper type, consistent with every scalar already being a generically-boxed `Object` in the VM.
- **`Instruction`** — a fixed-size `(Opcode, int operand)` record. Every instruction is the same shape regardless of opcode (opcodes that take no operand simply carry an unused `0`), so jump/call targets are always plain instruction indices, directly addressable with no decoding pass — unlike JVM-style variable-length bytecode.
- **`BytecodeFunction`** — metadata only (name, parameter count, slot count, `codeStart`), never its own instruction list — every function's code lives in one shared, flat, program-wide instruction stream, addressed by index.
- **`BytecodeStruct`** (v3 Milestone S4) — metadata only (name, field count), addressed by index from `NEW_STRUCT`'s operand exactly as `BytecodeFunction` is addressed by `CALL`'s. Mirrors `BytecodeFunction`'s role and shape; its one field (`fieldCount`) is what `NEW_STRUCT` needs to allocate and fill a struct's runtime `Object[]`. v3 Milestone S5 (field access) ended up needing zero changes here — a field's *index* (not its name or type) is all `ARRAY_GET`/`ARRAY_SET` need, and that index is resolved once, at code-generation time, directly from the AST's still-available `StructSymbol.fields()`; it never needs to survive into the compiled `BytecodeModule` at all, so this record still has nowhere it needs to grow field names/types into.
- **`BytecodeModule`** — the complete compiled program: a deduplicated constant pool, one `BytecodeFunction` per declared function, one `BytecodeStruct` per declared struct (since v3 Milestone S4), and the single shared instruction list. Defensively copies all four lists in its compact constructor.
- **`CodeGenerator`** — builder-style, mirroring `SemanticAnalyzer`/`SemanticModel`'s shape: mutable accumulators (constant pool with dedup via `constantIndex`, per-function local-slot map, function-index map, and — since v3 Milestone S4 — a struct-index map) filled in while walking the AST, assembled into one immutable `BytecodeModule` at the end (`generate()`). `generate()` assigns every function a stable index in declaration order, assigns every struct a stable index the same way (into a `Map<StructSymbol, Integer> structIndices` that belongs to `CodeGenerator` alone — `SemanticModel` carries no bytecode-layout information), emits the program's two-instruction entry stub (`CALL <index of main>; HALT` — always instructions 0 and 1, so the VM always knows where to start), then compiles each function in turn. Within a function, `compileFunction` assigns parameter and local-variable slots up front (before any instruction is emitted) and always emits a trailing unconditional `RETURN`, even when every path already returns, so a function never falls off the end of its own code. Forward jumps (`if`/`else`, `while`) use backpatching: a placeholder operand (`-1`) is emitted and remembered by instruction index, then overwritten in place (`instructions.set(index, new Instruction(...))`) once the true target is known — `Instruction`'s immutability means this replaces the list entry wholesale rather than mutating a field. `compileExpr`'s `NewStructExpression` case compiles arguments left-to-right (identical to `FunctionCallExpression`), then derives the `StructSymbol` from `semanticModel.expressionTypes().get(...).structName()` + `semanticModel.structTable()` (no separate resolution map) and emits `NEW_STRUCT <structIndex>`. v3 Milestone S5 added the one remaining private helper CodeGenerator has ever needed for structs, `fieldIndex(StructSymbol, String)` — a plain declaration-order linear scan of `struct.fields()`, computed fresh at every call site with no caching — and two new `compileExpr` cases built entirely on opcodes that already existed: `FieldAccessExpression` compiles its target, resolves the target's `StructSymbol` the same `expressionTypes()` + `structTable()` way `NewStructExpression` does (looking the target up, not the access expression itself), pushes the resolved field index as a constant, and emits `ARRAY_GET` — the identical opcode `ArrayAccessExpression` already used for `array[index]`, since a struct's `Object[]` and an array's `Object[]` are indistinguishable to the VM. `FieldAssignmentExpression` compiles the same way but with `compileExpr(value)` between the index push and a final `ARRAY_SET` — the identical opcode `IndexAssignmentExpression` already used, whose "push the assigned value back onto the stack" behavior is exactly what makes chained field assignment (`a.x = b.x = 5`) work with no new bookkeeping. No opcode was added, no existing opcode's semantics changed, and `Opcode`/`Instruction`/`VirtualMachine`/`Frame`/`BytecodeModule`/`BytecodeFunction`/`BytecodeStruct` all stayed at zero diff for this milestone — this is possible only because a struct's runtime representation was already "a plain `Object[]`, indexed by position" since S4; field access is that same fact read back out, with the field *name* resolved to a position entirely before the VM ever runs.

Never re-validates anything `SemanticModel` already resolved — a missing resolution at this stage means semantic analysis itself failed to catch something, and is treated as an internal invariant violation (`IllegalStateException`), not a user-facing diagnostic.

**Why this shape matters for self-hosting**: the project's long-term, not-yet-started goal is rewriting this compiler in GopiLang itself. A self-hosted compiler will need to represent its own AST nodes as structs and walk them by reading struct fields — which is exactly the capability S5 just added, and specifically the *minimal* version of it. Field access resolves entirely at compile time, to a plain integer index, reusing an opcode the VM already had — there's no new runtime concept (no field-metadata table, no reflective lookup, no vtable) for a future self-hosted compiler's own code generator to have to reproduce. The dependency runs one direction only: today's Java `CodeGenerator` needed to *understand* struct fields to compile `point.x`, but a GopiLang program doing the identical thing at self-hosting time asks nothing new of the VM that the S4 struct-as-`Object[]` representation didn't already provide. Each struct milestone so far — declarations (S1), the type system (S3), construction (S4), field access (S5) — has added exactly one new capability to the *language* while asking the *VM* for as little as possible (one opcode total, `NEW_STRUCT`, across all four), which is the same "small instruction set, all complexity resolved before the VM runs" principle the rest of the bytecode design already follows.

## `vm` — The Virtual Machine

**Responsibility**: execute a `BytecodeModule`.

- **`Frame`** — one call activation: the `BytecodeFunction` being run, its local-variable slots (sized by `slotCount()`), its own operand stack, and the return address to resume the caller at. Every active call gets its own `Frame`, which is what makes recursion work with no special-casing — two simultaneously-active calls to the same function simply have two distinct `Frame`s on the call stack.
- **`VirtualMachine`** — a `BytecodeModule`, a `Deque<Frame>` call stack, and a program counter (`pc`) indexing into the module's shared instruction list. `run()` is a fetch-decode-execute loop: fetch the instruction at `pc`, increment `pc`, dispatch on its opcode. `CALL` pops the callee's arguments off the caller's operand stack (last-pushed argument lands in the highest local slot, matching how `CodeGenerator` compiles arguments left-to-right), creates a new `Frame`, pushes it, and jumps to the callee's `codeStart`. `RETURN` pops the current frame, optionally carries one value back onto the (now-current) caller's operand stack, restores `pc` from the popped frame's return address, and terminates the program if no caller frame remains. Jump opcodes (`JMP`, `JMP_IF_FALSE`) simply overwrite `pc` with the instruction's operand — since `pc` is already incremented before the opcode dispatch runs, this assignment lands exactly on the target index with no extra bookkeeping. `NEW_STRUCT` (v3 Milestone S4) reads `module.structs().get(operand).fieldCount()`, allocates a fresh `Object[fieldCount]`, and pops that many values off the operand stack in reverse — the identical idiom `CALL` already uses for its own parameters — then pushes the array. `CALL`/`RETURN`/`LOAD`/`STORE` needed no changes at all for this: they already move plain `Object` values with zero type-specific logic, so a struct instance passes through them exactly as an array already does.

## `printer` — Debugging Views Over Compiler Output

**Responsibility**: render intermediate compiler artifacts as human-readable text, without affecting compilation itself.

- **`AstPrinter`** — renders a `Program` as a Unicode tree. Deliberately external to the `ast` package, dispatching with a plain `switch` over the sealed `Stmt`/`Expr` hierarchies rather than adding an `accept()` method to the AST nodes. Its `Parameter`/`VariableDeclaration`/`FunctionDeclaration` labels call `TypeRef.toString()` directly, unchanged since before S2 — `TypeRef` itself now renders a struct type's name (checking `structName` before `elementType`), so the S2-era `typeLabel()` workaround that lived here is gone.
- **`BytecodeDisassembler`** — renders a `BytecodeModule`'s constant pool, function table, struct table (since v3 Milestone S4), and instruction list as plain text (used by `gopic --disassemble`). Reuses the `BytecodeModule` a real `CodeGenerator` run already produced; it never regenerates or re-derives anything. `hasOperand(Opcode)` is an explicit allowlist (not exhaustive-by-default), so `NEW_STRUCT` had to be added there for its struct-index operand to print at all.

---

## `errors` — Diagnostics

**Responsibility**: the one thing that crosses phase boundaries.

- **`Diagnostic`** — an immutable record (phase, source range, message, suggestion) with a `render()` method that draws a source-line-and-caret view.
- **`DiagnosticReporter`** — a simple collector each phase owns independently (`Lexer`, `Parser`, `SemanticAnalyzer` each have their own — merging multiple phases' diagnostics into one combined view is left to the CLI, not each phase's job).
- **`ErrorPhase`** — which phase a diagnostic came from (`LEXICAL`, `SYNTAX`, `SEMANTIC`, `TYPE`, `RUNTIME`).
- **`GopiError`** — the abstract base for phase-local control-flow exceptions (`LexerException`, `ParseError`). These are internal signals only: thrown to unwind out of a broken token/statement, caught immediately within the same phase, and converted to a `Diagnostic` at the catch site. They never escape the phase that threw them, and semantic analysis has no subclass at all (see the `semantic` section above).

---

## `types` and `util` — Shared, Dependency-Free Support

- **`types.PrimitiveType`** — the five primitive types (`INT`, `FLOAT`, `BOOL`, `STRING`, `VOID`), used by the AST and semantic analysis. `toString()` returns these internal names, used by `--ast`/`--disassemble`'s developer-facing dumps; `displayName()` returns the GopiLang keyword spelling (`num`/`dec`/`flag`/`text`/`none`) instead, used everywhere a `Diagnostic` message shows a type to the user. `BinaryOperator`/`UnaryOperator` follow the same split, with `symbol()` returning the source operator (`+`, `!`, ...) instead of the enum name.
- **`util.SourceLocation`** — a single (line, column) position.
- **`util.SourceRange`** — a (start, end) span, used by every AST node and every `Diagnostic` to point at exactly the source text involved.

Both packages have zero dependency on any pipeline stage — they're pure, reusable value types.

## `cli` — The Command-Line Entry Point

**Responsibility**: orchestrate the pipeline for a single `.gopi` file; add no compiler behavior of its own.

- **`GopiC`** — `main()` dispatches on the command-line arguments to one of four modes: run a program end-to-end (default), or inspect one intermediate stage (`--tokens`, `--ast`, `--disassemble`) without executing the VM. All four modes share `compileToBytecode()`, which runs lexer → parser → semantic analyzer → code generator in sequence, stopping and printing diagnostics (with a non-zero exit code) the moment any phase reports an error, and never letting a later phase see output from a failed earlier one.
